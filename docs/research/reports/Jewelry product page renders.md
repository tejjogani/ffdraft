# Pin the render, unclamp the diamond

A Blender Cycles jewelry render is already repeatable to the last bit on one machine and one build, as long as the seed is fixed and no time limit is set. That was measured in Blender 5.3.0 on a 2-core CPU, in a lab of 349 renders: every fixed-seed repeat gave identical pixels, with the denoiser on or off and at one or two threads. The one exception was a single last-bit difference in a special tangent material. What stops the render workflow's stills from being true to life is three of its own settings and one wrong name. Glossy bounces at 16 leave about 18 % of a diamond's pixels more than 10 % too dark. The indirect clamp of 20 removed 39 % of the stone's light in the test studio, all of it sparkle. The AgX view cuts the chroma of yellow gold by about a third. And "Dispersion 0.36" names a socket that does not exist in Blender 5.3, so a script that sets it fails. Animations are built by turning the piece on a pivot under fixed lights, with linear keys on frame 1 and frame N+1, rendered as numbered PNG files and encoded with an explicit BT.709 conversion. The limits are plain. Nothing here was tested on a GPU, on Apple Metal, on macOS or on a second machine. The test scene was one small ring with one round diamond. Several platform rules, Amazon's above all, could not be opened and stay unverified.

Three labels are used throughout. **Measured** means a script ran in Blender 5.3.0 (the `bpy` module, build `02f0899d78e3`) or FFmpeg 6.1.1 on the test machine and the number came from its log. **Verified at a source** means a named page or source file was opened and the claim is on it. **Estimate** means reasoning or working knowledge that nobody tested. The measured scripts and logs sit in scratch folders outside the repository (`../spikes/23-render-tests/lab/`, `../spikes/23-render-tests/metals/`, `../spikes/23-render-tests/animation/`). Earlier research is cited by file name: `14-jewelry-rendering.md`, `15-own-renderer.md` and `18-low-end-machines.md`.

## Fixed seed and no time limit give bit-identical pixels on one machine

The first question was whether the same script gives the same picture twice. It does. With seed 0, 64 fixed samples and no time limit, the 32-bit float pixels and the 8-bit PNG pixels were **identical in all eight comparisons**: the same process twice, three fresh processes, two threads against one, each with Open Image Denoise off and then on ([exp01_repeat.py](../spikes/23-render-tests/lab/exp01_repeat.py), [log](../spikes/23-render-tests/lab/log_exp01.txt)). The workflow's adaptive sampling at threshold 0.01 also repeated exactly, across runs and across thread counts. Against a fixed 512-sample render it differed by at most 9/255 and saved 3 % of CPU time ([exp02_adaptive.py](../spikes/23-render-tests/lab/exp02_adaptive.py)). The source code explains why. Each pixel's random sequence is built only from the pixel's x and y and the scene seed. No thread, tile or clock enters ([pattern.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/sample/pattern.h)).

Two things broke repeatability in the tests. **A time limit** (`scene.cycles.time_limit = 10`) gave three different images in five runs, with pixels up to 154/255 apart, because the machine reached a different sample count each time. The saved metadata still said 4096 samples, so the file does not reveal the early stop ([log](../spikes/23-render-tests/lab/log_exp02_adaptive.txt)). **A changed seed** moved the stone crop by a mean of 2.4/255 even at 1024 samples (SSIM 0.97), far beyond any "same image" tolerance ([exp04_seed.py](../spikes/23-render-tests/lab/exp04_seed.py)). A third effect is real but tiny. The source still builds tangents in thread order on meshes above 10,000 faces ([mikktspace.hh](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/mikktspace/mikktspace.hh)), and a bug report traced run-to-run differences to that code ([issue 101726](https://projects.blender.org/blender/blender/issues/101726)). In the lab one of 16 two-thread renders of a 20,224-triangle ring with a UV-tangent material differed, in 3 of 65,536 pixels, by one float step. The 8-bit image was unchanged ([exp12_tangent.py](../spikes/23-render-tests/lab/exp12_tangent.py)).

Pixels repeat, but files do not. Blender writes the date and render time into every image, so no PNG, JPEG or EXR had the same file hash twice. With seven stamp flags off (`use_stamp_date`, `use_stamp_time`, `use_stamp_render_time`, `use_stamp_frame`, `use_stamp_camera`, `use_stamp_scene`, `use_stamp_filename`), PNG and JPEG written by `bpy.ops.render.render(write_still=True)` were byte-identical across fresh processes. There is a trap: also setting `use_stamp_labels = False` brings the time strings back ([exp03c_stamp_matrix.py](../spikes/23-render-tests/lab/exp03c_stamp_matrix.py)). **OpenEXR files never repeated** under any flag set, although everything after the header was identical ([exp03b_exr_header.py](../spikes/23-render-tests/lab/exp03b_exr_header.py)). The safe rule is to hash decoded pixels, not files.

Across machines the claim weakens, and here the evidence is from sources only. Blender's own render tests compare each GPU backend to stored references with a tolerance, not a hash: a test fails only if more than 1 % of pixels differ by more than 0.016 on a 0 to 1 scale ([cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py), [render_report.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/modules/render_report.py)). The Open Image Denoise documentation allows "small numerical differences" between devices ([OIDN README](https://raw.githubusercontent.com/RenderKit/oidn/master/README.md)). The OptiX denoiser lives in the NVIDIA driver and changes with driver updates, so it cannot be pinned ([NVIDIA developer forum](https://forums.developer.nvidia.com/t/optix7-denoiser-different-results-with-different-version-of-drivers/117989)). The device choice hides in user preferences: `scene.cycles.device = 'GPU'` with no GPU enabled there renders on the CPU without an error ([device.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/device.cpp)). So a render's identity is the Blender build, the device type, the backend and the hardware ray-tracing setting together. A GPU kit render should be described as close to the CPU preview, never as the same picture. No test here says how close.

The Blender version is itself a setting. The two dispersion sockets exist only from 5.3.0 ([Principled BSDF source at 5.3.0](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/nodes/shader/nodes/node_shader_bsdf_principled.cc)). The bundled denoiser moved from OIDN 2.3.3 in 5.0 to 2.4.1 in 5.1 and 2.5.0 in 5.2 and 5.3 ([versions.cmake at 5.3.0](https://raw.githubusercontent.com/blender/blender/v5.3.0/build_files/build_environment/cmake/versions.cmake)). The `bpy` package on PyPI carries exact builds, so `bpy==5.3.0` is a pin ([PyPI](https://pypi.org/pypi/bpy/json)). Blender 5.3 is not the long-term release; 5.2 LTS is, with support to July 2028 ([blender.org](https://www.blender.org/releases/5-2/)). The workflow needs 5.3 for diamond fire, so it leaves the LTS track knowingly. Other hidden inputs were found in the source and not tested: an `OCIO` or `BLENDER_OCIO` environment variable replaces the colour configuration ([colormanagement.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/imbuf/intern/colormanagement.cc)), and the Object Info "Random" value is a hash of the object's name ([object.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/object.cpp)).

## Three workflow settings measurably dull the diamond

The test scene was the ring from `15-own-renderer.md` section 6: a 6.5 mm, 57-facet round brilliant in a four-prong yellow gold ring, with four soft boxes and three small sparkle panels. The baseline was the workflow's own settings, changed one at a time ([lab.py](../spikes/23-render-tests/lab/lab.py)).

**Glossy bounces.** Cycles counts every reflection inside a stone as a glossy bounce and ends the path when that counter hits its limit ([path_state.h](https://github.com/blender/blender/blob/main/intern/cycles/kernel/integrator/path_state.h)). The workflow sets total 32, transmission 32 and glossy 16. At 1024 samples that gave almost the same stone as 16 all round (0.8 % apart). Raising glossy to 32 lifted the stone's mean light by 3.1 % and re-lit **17.7 % of stone pixels that had been more than 10 % too dark**: a band of small crown facets that showed black. It cost about 8 % more CPU time per sample. Raising total and transmission to 64 while glossy stayed at 16 changed nothing, to the bit ([exp05_depth.py](../spikes/23-render-tests/lab/exp05_depth.py), [log](../spikes/23-render-tests/lab/log_exp05_depth.txt)). The earlier ray-count spike agrees in kind: about 4 % of the light that enters a diamond is still inside after 16 facet hits (`14-jewelry-rendering.md` section 4.2).

**Indirect clamp.** Every flash inside a stone is light reached after a bounce, so the indirect clamp acts on it. With the clamp off at 1024 samples, 103 stone pixels (0.31 %) carried **39.1 % of the stone's summed light**. Their level was the same at two seeds and two sample counts, so they are real reflections of the sparkle lights, not fireflies. With clamp 20 no stone pixel reached display white, and the brightest 8-bit value was 244. The price of removing the clamp was noise: about six times the linear noise in the stone, and isolated bright pixels on metal and ground up from about 90 to about 140 ([exp06_clamp.py](../spikes/23-render-tests/lab/exp06_clamp.py), [log](../spikes/23-render-tests/lab/log_exp06_clamp.txt)). The Blender manual says the same in words: clamping can dim things meant to be bright, such as lights and reflections ([Light Paths](https://docs.blender.org/manual/en/latest/render/cycles/render_settings/light_paths.html)). This result depends on the lights. The workflow's own strip softboxes were not rendered, and no clamp value between 20 and off was tried.

**Dispersion.** Blender 5.3.0 has no socket called "Dispersion". It has `Transmission Dispersion Scale` (default 0) and `Transmission Dispersion Abbe Number` (default 20) ([log_inspect_bpy.txt](../spikes/23-render-tests/lab/log_inspect_bpy.txt)). The two combine as scale divided by Abbe number. Scale 0.3617 at Abbe 20 matched scale 1.0 at Abbe 55.3, with a mean difference of 0.085/255. So the workflow's "0.36" is the right strength for diamond only if the Abbe number stays at its default. Dispersion cost no time per sample, but it raised noise in the stone 4.4 times ([exp07_dispersion.py](../spikes/23-render-tests/lab/exp07_dispersion.py)). The Khronos glTF dispersion extension lists the same pair for diamond, Abbe 55 and 0.36 ([Khronos](https://github.com/KhronosGroup/gltf/blob/main/extensions/2.0/Khronos/KHR_materials_dispersion/)).

**Two settings did nothing measurable.** Filter Glossy at 0.2 against 0 changed the stone by 0.11/255. Caustics on left the stone unchanged and added a mean of 0.57/255, with more noise, to the ground ([log](../spikes/23-render-tests/lab/log_exp06_clamp.txt)).

**The denoiser is safe above about 256 samples.** Open Image Denoise at 64 samples was as close to a 4096-sample reference as 256 samples without it. Facet edges stayed sharp and in place. What went soft was the fine detail inside facets, which turned into pastel patches. At 256 samples that detail was back, and at 1024 samples the denoiser changed almost nothing ([exp08_denoise.py](../spikes/23-render-tests/lab/exp08_denoise.py), [log](../spikes/23-render-tests/lab/log_exp08_denoise.txt)). The workflow's 160-sample finals sit between the two tested points.

**Base colour and absorption.** A separate small test found that the Principled `Base Color` multiplies light once per pass through a stone, whatever its thickness. The node default of 0.8 passed 80 %. Volume Absorption follows exp(−density × (1 − colour) × distance), with distance in scene units, so at 1 unit = 1 mm the density is per millimetre ([tiny_tests.py](../spikes/23-render-tests/metals/tiny_tests.py)). The workflow's table gives no base colour for diamond. If its scripts leave the default, every diamond is 20 % too dark. The library code was not available to check.

**Gold and the view transform.** The workflow's "AgX - Base Contrast" look is the same picture as AgX with no look: 17 to 40 of 65,536 pixels differed by 1/255. Under AgX the gold's chroma (CIELAB C*) was 17.0, against 25.2 under Standard and 30.0 under Khronos PBR Neutral. To the eye the AgX gold read as pale brass ([exp10_colour.py](../spikes/23-render-tests/lab/exp10_colour.py), [log](../spikes/23-render-tests/lab/log_exp10_colour.txt)). The Blender manual describes Khronos PBR Neutral as aimed at product photography ([Color Management](https://docs.blender.org/manual/en/4.3/render/color_management.html)), and its designers built it so base colours pass through unchanged and highlights fade to white without a hue shift ([model-viewer](https://modelviewer.dev/examples/tone-mapping)). No render was compared with a photograph of real gold, so "more saturated" is measured and "more correct" is not.

**Metal colours.** One note reduced measured metal spectra from the CC0 refractiveindex.info database to linear RGB ([database](https://github.com/polyanskiy/refractiveindex.info-database)). The method reproduced Blender's built-in titanium values within 1 %. It puts rhodium at base colour (0.797, 0.765, 0.742). The workflow's white metal is a neutral (0.86, 0.86, 0.86): 4 L* units brighter than rhodium and with no warmth, which reads as chrome. The workflow's "18K" yellow has the saturation the same method gives 22K to 24K gold, and its rose gold is too pink and too little yellow. These are calculations from published data, not Blender renders, and the karat alloy figures carry an error of about ΔE 5, because no measured data exists for gold-silver-copper alloys. A published measurement of a red gold alloy gives a* of 6.5 to 7.2, against 10.9 for the workflow's rose ([Gold Bulletin 2013](https://link.springer.com/article/10.1007/s13404-013-0089-6)).

**Depth of field.** Cycles reads the f-stop as if one scene unit were one metre. In the workflow's millimetre scenes "f/16" produced no measurable blur, and f/0.016 produced the blur of a real f/16 lens. The unit scale setting made no difference ([tiny_tests.py](../spikes/23-render-tests/metals/tiny_tests.py)). So the workflow's "f/11" and "100 mm at f/4" do nothing today. For catalogue shots that is the right look: photographers focus-stack rings because one frame holds only a few millimetres sharp ([Visual Education](https://visualeducation.com/jewellery-photography-top-tips-for-how-to-photograph-jewellery/)).

**Lighting.** The workflow's rule that diamonds need dark and bright structure matches what photographers and gemologists say. GIA's photographers use diffused light for metal and body colour and direct light for fire ([GIA](https://gia.edu/gem-photography)). The diamond trade press warns against tenting a stone in white ([Rapaport](https://rapaport.com/?p=40092)). The earlier spike saw the consequence in Cycles: a studio bright all round gave believable facets but no arrow pattern, because nothing dark sat above the table (`15-own-renderer.md` section 6.4). Specific light sizes and strengths in the notes are estimates. No source gives measured figures for a jewelry set.

## Product pages want 2,000-pixel squares on exact white, and some want a photo

The pixel rules agree closely. Shopify recommends 2048 × 2048 px ([Shopify Help](https://help.shopify.com/en/manual/products/product-media/product-media-types)). Etsy recommends at least 2000 px each way and sRGB ([Etsy Help](https://help.etsy.com/hc/en-us/articles/115015663347-Requirements-and-Best-Practices-for-Images-in-Your-Etsy-Shop)). Amazon's seller blog asks for pure white, RGB 255, 255, 255, more than 1,000 px per side for zoom, and advises 85 % fill ([sell.amazon.com](https://sell.amazon.com/blog/product-photos)). Google asks for 75 to 90 % fill and recommends about 1500 px ([Google Merchant Center](https://support.google.com/merchants/answer/6324350?hl=en)). One retailer's jewelry guide asks for 2000 px minimum, pure white with **no grounding shadow and no surface reflection**, and at least 85 % fill ([Kohl's vendor guide](https://link.kohls.com/content/dam/klink/pdfs/Vendor-Style-Guide-Jewelry.pdf)). The workflow's 1600 px finals and "about 70 %" fill fall short of these.

Exact white was measured. Rendering with a transparent film over a shadow catcher and compositing over #FFFFFF outside Blender gave a corner value of exactly 255 under every view transform tested, with 99.4 to 99.8 % of ground pixels at 255 and the rest a soft contact shadow. An opaque white floor reached 255 only under the Standard view ([log](../spikes/23-render-tests/lab/log_exp10_colour.txt)). The workflow already uses this method. It needs a second export without the shadow for marketplaces that forbid one.

The harder rules are about what a picture is. Etsy's image policy, updated 22 October 2026, requires at least one unedited photograph of the actual item for most products. It does not name renders at all ([Etsy policy](https://www.etsy.com/legal/policy/listing-image-requirements/253962679005)). A render-only Etsy listing does not meet that policy as written. Google bars "line art, mockups, or illustrations that don't depict the physical product" on the main image and does not say whether a faithful CAD render counts ([Google](https://support.google.com/merchants/answer/6324350?hl=en)). Google also requires a metadata tag on generative-AI images, and its pages do not mention 3D renders ([Google AI content policy](https://support.google.com/merchants/answer/14743464?hl=en-IE)). A path-traced CAD render is not generative AI, so on the notes' reading that tag does not apply; Google has not said so. Amazon staff posts say "no illustrations" ([Amazon forum](https://sellercentral.amazon.com/seller-forums/discussions/t/13af96ea-6b07-4bf9-8dbe-a13292c2e3b1)) and that all images must accurately represent the product ([Amazon forum, Quick Tip](https://sellercentral.amazon.com/seller-forums/discussions/t/ab884127-f9b4-4053-8096-4991e1d60d1f)). A seller's direct question about 3D renders went unanswered ([Amazon forum thread](https://sellercentral.amazon.com/seller-forums/discussions/t/0149bdb3-2056-42ce-b0bb-9eef94e3d2b8)).

Law looks at the impression, not the method. The US FTC Jewelry Guides cover depictions by any means and judge the net impression. They carry one image-specific note: a picture that shows a diamond or gemstone larger than its actual size may mislead unless the true size is disclosed ([16 CFR Part 23](https://www.ecfr.gov/current/title-16/chapter-I/subchapter-B/part-23)). A macro render enlarges every stone, so millimetre sizes and carat weight belong near the gallery. This fits the workflow's own rule. Its verification step already measures stone counts, diameters and carat weight from the mesh, and those are the numbers a disclosure needs. None of this is legal advice, and a lawyer should read the cited rules.

Shoppers want scale and zoom more than motion. In Baymard's testing 42 % of users tried to judge size from product images, and users often skipped videos ([Baymard](https://baymard.com/blog/in-scale-product-images)). Real-time 3D viewers are a poor stand-in for stones: the Khronos dispersion extension itself notes that gems have many internal reflections that a real-time rasteriser does not capture ([Khronos](https://github.com/KhronosGroup/gltf/blob/main/extensions/2.0/Khronos/KHR_materials_dispersion/)). A pre-rendered spin or loop keeps the path-traced look.

## Turntables: turn the piece, key frame N+1, and expect no temporal denoiser

**Build.** The following was run through the Blender 5.3.0 scripting interface with no renders ([anim_api_test.py](../spikes/23-render-tests/animation/anim_api_test.py)). New keyframes default to Bézier easing and must be set to `LINEAR` for a loop. With keys at frame 1 (0°) and frame N+1 (360°) and N = 144, each frame steps exactly 2.5°. Putting the last key on frame N gives a 2.5175° step and makes the last frame a copy of the first: one stuck frame per loop. Scripts written for Blender 4.x break here, because `Action.fcurves` was removed in 5.0 ([5.0 change log](https://docs.blender.org/api/5.0/change_log.html)). Curves are reached through `bpy_extras.anim_utils.action_get_channelbag_for_slot`.

**What turns.** GIA defines sparkle as flashes seen when the diamond, the observer or the light source moves ([GIA, 2004](https://www.gia.edu/articles/fall-2004-grading-cut-quality-brilliant-diamond-moses)). Turning the piece under fixed lights and a fixed camera is a physical turntable: every facet passes through every light. The notes recommend this for the product loop and a camera orbit only for short arcs. That is reasoning. No source that could be opened states it.

**Sparkle speed is an estimate.** A facet acts as a mirror, so a light of apparent width α stays in one facet for α/2 of rotation. At 2.5° per frame a 3° light flashes for 0.6 of a frame, which reads as strobing. At 1° per frame or less it lasts 1.5 frames or more. This is the notes' own geometry, with no source and no test. It suggests two shots: a faster full spin lit for shape, and a slower rock or light sweep for sparkle.

**Flicker.** Blender 5.3 has no temporal denoiser in its normal render path. It bundles Open Image Denoise 2.5.0, which works one frame at a time ([versions.cmake](https://raw.githubusercontent.com/blender/blender/v5.3.0/build_files/build_environment/cmake/versions.cmake)). The one temporal route is an OptiX operator with no interface, which needs an NVIDIA card and loses fine detail in user tests ([BlenderNation](https://www.blendernation.com/2022/01/10/optix-temporal-denoising-support-added-to-blender-3-1-alpha/), [developer forum](https://devtalk.blender.org/t/taking-a-look-at-optix-7-3-temporal-denoising-for-cycles/18656?page=6)). The manual recommends an animated seed for animation ([Sampling, 4.5](https://docs.blender.org/manual/en/4.5/render/cycles/render_settings/sampling.html)). The measurement disagrees for one case. On static ground beside a turning ring, with the denoiser on, a fixed seed changed by 0.037 to 0.040 of 255 per frame and an animated seed by 0.054 to 0.071. Without the denoiser the gap was 0.001 against 1.07 to 1.73 ([exp09_flicker.py](../spikes/23-render-tests/lab/exp09_flicker.py), [log](../spikes/23-render-tests/lab/log_exp09_flicker.txt)). Both denoised figures are under 0.1/255, so the practical case for a fixed seed on a locked camera is that it is steadier and exactly repeatable. The known objection, a still noise pattern under a moving object, was not measured. The test was six frames at 256 px and 32 samples.

**Render and check.** Blender's manual gives the recipe for sharing a frame folder between machines: overwrite off, placeholders on ([Output](https://www.blender.org/manual/en/render/output/properties/output.html)). Rendering numbered images, never a video file, means a crash costs one frame. The checks run cheapest first. Evaluate the pivot curve with no render. Make a contact sheet of key frames. Then render 8 to 10 consecutive frames at final settings, because a still can look clean while the sequence flickers ([iRender](https://irendering.net/blender-cycles-denoising-animation-oidn-optix/)). After the render, a small script run on 150 synthetic frames flagged a 3 % brightness pop at 14 robust standard deviations and a duplicated frame at −31 or beyond. It did **not** flag one noisier frame inside fast motion, and a dead machine's zero-byte placeholder passed a missing-number check ([../spikes/23-render-tests/animation/](../spikes/23-render-tests/animation/)). File sizes must be checked, and a person still has to watch the loop.

**Cost.** Per-frame cost on the test CPU was about 2.1 CPU-seconds per sample per megapixel for a stone close-up ([exp11_timing.py](../spikes/23-render-tests/lab/exp11_timing.py)). GPU figures are estimates from `18-low-end-machines.md`: a 150-frame 1080p turntable at 192 to 256 samples takes 1 to 7 hours on an M2 MacBook Air GPU and about 7 to 70 minutes, for $0.15 to $1.05, on a rented T4, L4 or RTX 4090. Those rest on Blender Open Data median scores (M2 10-core GPU 354, RTX 4090 11,679), not on a timed jewelry frame ([Blender Open Data](https://opendata.blender.org/benchmarks/query/?device_name=Apple%20M2&group_by=device_name&group_by=blender_version&group_by=compute_type&response_type=datatables)). The workflow's "10 to 20 minutes on a decent GPU" holds only for the fast end of that range.

## An untagged encode shifts greens by 15 %; an explicit BT.709 conversion fixes it

The workflow's encode line converts with `-pix_fmt yuv420p` and nothing else. On FFmpeg 6.1.1 that used the BT.601 matrix. Read back the way an HD player decodes, pure green (0, 255, 0) came out as (0, 215, 0) and a green stone colour (8, 204, 77) as (0, 176, 72). Adding colour tags without a conversion left the pixels wrong and the file confidently labelled. An explicit `scale=out_color_matrix=bt709:out_range=tv` filter plus matching tags gave (0, 254, 0) and (7, 203, 76) ([../spikes/23-render-tests/animation/](../spikes/23-render-tests/animation/)). The Academy Software Foundation's encoding guide recommends the same conversion, with the transfer tagged as sRGB so the video matches the sRGB stills in browsers, and a CRF near 18 for H.264 ([ASWF, H.264](https://academysoftwarefoundation.github.io/EncodingGuidelines/Encodeh264.html), [ASWF, web colour](https://academysoftwarefoundation.github.io/EncodingGuidelines/WebColorPreservation.html)). The same guide notes that FFmpeg 7.1 changed how output colour options behave ([ASWF, colour](https://academysoftwarefoundation.github.io/EncodingGuidelines/ColorPreservation.html)). The current release is 8.1.2, and these commands were run only on 6.1.1.

H.264 in `yuv420p` MP4 is the file that plays everywhere. `-movflags +faststart` lets playback begin before the download ends ([FFmpeg wiki](https://fftrac-bg.ffmpeg.org/wiki/Encode/H.264)). AV1 and HEVC are smaller first choices, and HEVC needs the `hvc1` tag for Apple players ([ASWF, HEVC](https://academysoftwarefoundation.github.io/EncodingGuidelines/EncodeHevc.html)). On the page the element is `<video autoplay loop muted playsinline>` with a poster. iOS Safari autoplays only muted video and opens it fullscreen without `playsinline` ([WebKit](https://webkit.org/blog/6784/new-video-policies-for-ios/)). Shopify's `video_tag` sets autoplay, loop and muted to false by default, so a theme must switch them on ([shopify.dev](https://shopify.dev/docs/storefronts/themes/product-merchandising/media/support-media)). Transparent video needs two files and has mobile bugs ([browser test, 2024](https://jakearchibald.com/2024/video-with-transparency/)). Rendering the loop on the page's own background colour avoids it.

A drag-to-rotate spinner is the same turntable delivered as stills. One open-source viewer defaults to 36 frames in its examples and warns against more than 30 to 40 full-size frames on phones, because each decoded frame costs about 4 MB of memory ([js-cloudimage-360-view](https://cdn.jsdelivr.net/npm/js-cloudimage-360-view@4.9.5/README.md)). A 144-frame render serves both: all frames for the video, every second or fourth frame for a 72- or 36-frame spinner. The first gallery still should load as a plain, high-priority image, and video and spin should wait behind a poster ([web.dev](https://web.dev/articles/fetch-priority)). The file sizes in the notes come from a synthetic test sequence, not from rendered jewelry, and are left out here.

## What was not tested, and what could not be opened

**No GPU of any kind was tested**: no CUDA, OptiX, HIP or oneAPI, and no Apple Metal. No macOS machine was used. No second machine, CPU model, operating system or Blender build was compared. Every repeatability result is the same binary on the same 2-core Linux virtual machine. Nothing here shows that a GPU render repeats, or how far it sits from a CPU render.

**The test scene was one small scene.** It held one 6.5 mm round brilliant, one yellow gold ring and one studio with three small, very bright panels. Coloured stones, pavé, step cuts, white metal, HDRI lighting, depth of field on real pieces and motion blur were not rendered. The largest lab render was 512 px; the workflow's 1600 px finals were not rendered. The workflow's own light rigs were not rendered, and its library code was not read, so two findings (the clamp and the base colour) are conditional on what that code does. The 4096-sample reference used the workflow's own depth and clamp, so it measures noise, not physical truth. Metal colours were computed, not rendered and not compared with real swatches.

**Animation tests were narrow.** Keyframe behaviour was tested through the scripting interface without rendering. Flicker was measured on six small frames. The encode and check commands ran on synthetic frames with FFmpeg 6.1.1. No browser was used. HEVC with alpha could not be produced on Linux.

**Platform and legal pages that could not be opened.** Amazon's Seller Central image requirements (help pages G1881, G17811 and G9FUUH87RBNXGKB7) returned empty shells, so Amazon's current wording on zoom, cropping, jewelry and computer-generated images is unverified. No current Amazon jewelry style guide was found. Amazon India and other Indian marketplaces were not researched. Meta's help article on image rules was blocked. India's CCPA guideline text was read only through a press release, and the status of the ASCI draft on AI labelling after its June 2026 consultation is unknown. No page states how Shopify, Amazon, Google or Meta treat embedded colour profiles. Browser codec support tables were not opened. Named retailers' product pages were not opened, so their shot conventions are working knowledge. Most Blender 5.x manual pages and the 5.3 rendering release notes were blocked; setting facts come from the 5.3.0 source and the running module instead.

## Conclusion

The workflow's rule, "verifiable, no hallucination", now has a render-side form. A picture is verifiable when its seed, sample count, device and build are recorded, its decoded pixels are hashed, and nothing in the settings cuts off light the CAD and the physics would deliver. The tests show the first half is nearly free: Cycles on one CPU build is already exact. The second half costs render time and noise, roughly 8 % for full glossy depth and several times the stone noise for an open clamp, and that trade is worth making for stills and worth holding back for animation.

The open risk has moved off the test machine. The stills this workflow sells are rendered on the user's GPU from a kit, and every number here stops at the CPU. The cheapest next step is one frame of the test ring rendered on that Mac with Metal and compared against the CPU pixels with a stated tolerance. Until that exists, the final message for any GPU render should say "close to the verified preview", not "the same".

## Prioritised changes to the render workflow

Each change gives the current text, the new setting, and the evidence in three parts. Every property and socket name below was read back in `bpy` 5.3.0 (build `02f0899d78e3`) while this report was written. Priority 1 fixes errors. Priority 2 changes what the stone and metal look like, with measurements behind each. Priority 3 makes results repeatable and checkable. Priority 4 covers animation and delivery. Priority 5 holds estimates that need a test before they become rules.

### Priority 1: errors

**1. Name the real dispersion sockets.**
- Current: "Diamond (white): transmission 1, roughness 0, IOR 2.417, Dispersion 0.36"; emerald "dispersion 0.03"; sapphire/ruby "dispersion 0.05".
- New: on the Principled BSDF set `inputs["Transmission Weight"] = 1.0`, `inputs["Roughness"] = 0.0`, `inputs["IOR"] = 2.417`, `inputs["Transmission Dispersion Scale"] = 1.0`, `inputs["Transmission Dispersion Abbe Number"] = 55.0`. Write every stone as Scale 1.0 plus its own Abbe number.
- Measured: no socket named "Dispersion" exists, so a script that sets it fails. Scale 0.3617 at Abbe 20 matches scale 1.0 at Abbe 55.3, with a mean difference of 0.085/255 (two seeds differ by 8.3/255). Scale 0.36 at Abbe 55.3 is visibly paler. Dispersion adds no time per sample and 4.4 times the stone noise ([exp07](../spikes/23-render-tests/lab/log_exp07_dispersion.txt)).
- Verified at a source: both sockets and their defaults (0.0 and 20.0) are in the 5.3.0 source ([source](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/nodes/shader/nodes/node_shader_bsdf_principled.cc)). Khronos lists diamond at Abbe 55 ([Khronos](https://github.com/KhronosGroup/gltf/blob/main/extensions/2.0/Khronos/KHR_materials_dispersion/)). Trade dispersion figures for other stones are published ([International Gem Society](https://gemsociety.org/article/diamond-and-simulant-comparison-chart)).
- Estimate: Abbe numbers derived from trade dispersion by formula: sapphire and ruby 72 to 73, emerald 71, moissanite 25 to 27, cubic zirconia 30 to 34. On that reading the workflow's 0.03 and 0.05 are six to nine times too weak.

**2. State the stone's base colour.**
- Current: the materials table gives no base colour for diamond.
- New: `inputs["Base Color"] = (1.0, 1.0, 1.0, 1.0)` on every transmissive stone. Colour comes only from the Volume Absorption node (`inputs["Color"]`, `inputs["Density"]`).
- Measured: the node default is (0.8, 0.8, 0.8). Base colour 0.8 passed 80 % of light and 0.25 passed 25 %, whatever the thickness ([tiny_tests.py](../spikes/23-render-tests/metals/tiny_tests.py)).
- Verified at a source: none beyond the measurement.
- Estimate: whether the workflow's library leaves the default is unknown, because the library was not read. Check `to_blender` before claiming a 20 % gain.

**3. Pin the Blender build.**
- Current: `pip install --break-system-packages bpy rhino3dm scipy   # bpy = Blender as a Python module (5.x), Cycles CPU`.
- New: `pip install bpy==5.3.0` on Python 3.13. First lines of every render script: stop unless `bpy.app.version == (5, 3, 0)`, and write `bpy.app.version_string` and `bpy.app.build_hash` into `verification.json`. The kit README names the same build.
- Measured: every test ran on `bpy` 5.3.0, build `02f0899d78e3` ([log_inspect_bpy.txt](../spikes/23-render-tests/lab/log_inspect_bpy.txt)).
- Verified at a source: PyPI carries exact builds and 5.1+ wheels need Python 3.13 ([PyPI](https://pypi.org/pypi/bpy/json)). Dispersion sockets first appear at 5.3.0. The bundled denoiser version changes between releases ([versions.cmake](https://raw.githubusercontent.com/blender/blender/v5.3.0/build_files/build_environment/cmake/versions.cmake)).
- Estimate: 5.3 is not the LTS, so this pin trades long-term support for diamond fire. Whether two patch builds give identical pixels was not tested.

### Priority 2: settings that change the picture

**4. Raise glossy bounces to match the total.**
- Current: "max bounces 32, transmission 32, glossy 16, diffuse 3".
- New: `scene.cycles.max_bounces = 32`, `scene.cycles.glossy_bounces = 32`, `scene.cycles.transmission_bounces = 32`, `scene.cycles.diffuse_bounces = 3`.
- Measured: glossy 32 re-lit 17.7 % of stone pixels that were more than 10 % too dark, raised the stone mean 3.1 %, and cost 7.7 % more CPU per sample. Total 64 with glossy 16 was bit-identical to the current setting ([exp05](../spikes/23-render-tests/lab/log_exp05_depth.txt), [exp11](../spikes/23-render-tests/lab/log_exp11_timing.txt)).
- Verified at a source: Cycles counts each internal reflection as a glossy bounce ([path_state.h](https://github.com/blender/blender/blob/main/intern/cycles/kernel/integrator/path_state.h)).
- Estimate: 64/64/64 for hero close-ups (measured +1.8 % light for +15 % time on this stone). Pavé and step cuts were not tested.

## Corrections found after this report was written

The updated render workflow's code blocks were run in Blender 5.3.0, and its ffmpeg lines on 144 test frames, before it was published. Two things in the notes behind change 16 and section "Turntables" turned out wrong:

- **The pivot recipe moves the piece.** Read straight after `piv.location = centre`, the pivot's world matrix is still the identity, so parenting with its inverse shifts the piece by `centre` (measured: an object at (5, 6, 7) ended at (6, 8, 10)). Calling `bpy.context.view_layer.update()` before the parenting loop fixes it (the object stayed at (5, 6, 7)). The key step and the frame N+1 rule are unaffected: the measured step was 2.49996° to 2.50001° over 144 frames.
- **Spin frames made straight from transparent frames come out on black.** The corner pixel was (0, 0, 0). Laying the frames over white first, as the encode lines do, gave (255, 255, 255) and 72 frames from 144.
