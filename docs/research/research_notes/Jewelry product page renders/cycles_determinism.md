## 1. Seeds and sampling: what `seed`, `use_animated_seed`, the sampling pattern, `samples`, adaptive sampling and `time_limit` do to repeatability; which settings make a render depend on machine speed or thread count

### Takeaway
In 5.3 the per-pixel random sequence is a pure function of pixel coordinates, `scene.cycles.seed`, the sampling pattern and the sample count, so the sampler itself does not depend on threads, tiles or speed. The settings that tie the picture to the machine are `time_limit` (wall clock), multi-device rendering (work is split by measured speed), and one piece of multithreaded scene preparation (tangent generation on meshes above 10,000 faces) that still accumulates floats in thread order.

### Cited Findings
- [V] `scene.cycles.seed` is an integer, range 0 to 2147483647, default 0, described as the value that selects the noise pattern. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] `scene.cycles.use_animated_seed` defaults to False. When it is on, the seed handed to the integrator becomes a hash of the current frame number and the user seed (plus a subframe term), so the same file rendered at a different frame number gets different noise. — [sync.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/sync.cpp)
- [V] The kernel initialises each pixel's random state only from the pixel's x and y and the integrator seed: a pixel hash XOR seed for the Sobol patterns, and a scrambled Morton index of (x, y) with the seed for the blue-noise patterns. No thread id, tile id, device id or clock enters. — [kernel/sample/pattern.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/sample/pattern.h)
- [V] `scene.cycles.sampling_pattern` in 5.3 offers `AUTOMATIC` (the default), `TABULATED_SOBOL` (shown in the UI as "Classic") and `BLUE_NOISE`; three more (`SOBOL_BURLEY`, `BLUE_NOISE_FIRST`, `BLUE_NOISE_ROUND`) appear only with the developer/debug UI enabled. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] `AUTOMATIC` resolves differently by context: a final (non-viewport) render gets pure blue noise, the interactive viewport gets "blue noise for the first sample, then Sobol". A viewport render and an F12/headless render of the same scene therefore do not share a noise pattern. A debug-only pattern left in a file is silently replaced by pure blue noise when the developer UI is off. — [sync.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/sync.cpp)
- [V] The sample count is part of the pattern: the blue-noise sequence length is set to the (clamped) AA sample count, and the Sobol index mask and table size are derived from the next power of two of the sample count. Changing `scene.cycles.samples` therefore changes the sequence itself, not just how far along it the render goes. With blue noise the seed is additionally hashed before use. — [scene/integrator.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/scene/integrator.cpp)
- [V] Blue-noise sampling arrived in Blender 4.2 LTS; new files use it by default and existing files keep the classic pattern until changed by hand. — [Blender 4.2 LTS Cycles release notes](https://developer.blender.org/docs/release_notes/4.2/cycles/)
- [V] The Cycles add-on's file-versioning code forces `sampling_pattern = 'TABULATED_SOBOL'` when it opens a file saved by 4.2.52 or older (and again for files from 3.5.3 or older, where it also switches the light tree off if it was never set). Opening an old file in a new Blender therefore rewrites sampling settings on load. — [version_update.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/version_update.py)
- [V] Defaults in 5.3: `samples` 4096, `use_adaptive_sampling` True, `adaptive_threshold` 0.01 (0 means automatic from the sample count), `adaptive_min_samples` 0 (0 means automatic from the threshold), `time_limit` 0.0 (off). — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] `scene.cycles.time_limit` caps render time, not counting scene synchronisation. The limit is handed to the scheduler for each tile (the session's overall figure is the limit times the tile count), and the scheduler stops issuing work once the wall-clock limit is reached. The number of samples a pixel receives then depends on how fast the machine is. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [session.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/session/session.cpp), [render_scheduler.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/render_scheduler.cpp)
- [V] Adaptive sampling's convergence test runs at sample indices fixed by the adaptive step and `adaptive_min_samples`, not by elapsed time: the scheduler trims each batch so it ends exactly on a filter sample. A code comment states the aim that the final render be pixel-matched whatever the device's samples-per-second, and leaves a TODO for extra clamping to guarantee no filter point is skipped. — [adaptive_sampling.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/adaptive_sampling.cpp), [render_scheduler.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/render_scheduler.cpp)
- [V] The convergence decision compares accumulated float pixel values against the threshold, and the follow-up x/y filter re-opens neighbours of unconverged pixels inside the buffer window it is handed. — [kernel/film/adaptive_sampling.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/film/adaptive_sampling.h)
- [V] `scene.cycles.use_auto_tile` is marked deprecated in 5.3 because tiling can no longer be switched off; `scene.cycles.tile_size` defaults to 2048 and tiles are cached to disk during the render. Blender 5.0's notes say the Use Tiling option was removed and that raising the tile size is the way to effectively switch tiling off. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [Blender 5.0 Cycles release notes](https://developer.blender.org/docs/release_notes/5.0/cycles/)
- [V] With more than one render device, Cycles splits the image between devices by weight and re-balances those weights from the time each device spent. — [path_trace.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/path_trace.cpp)
- [V] Bug report #101726 (reported on Ubuntu with an RTX 2070 Super, also reproduced on CPU): two renders of one scene on one machine differed slightly. The cause was traced to scene preparation, not to the sampler or the GPU: two multithreaded routines that add floats atomically in whatever order threads arrive (normal and tangent calculation). Launching with `blender -t 1` gave identical results; the thread says normal-map tangents were still unsolved. Quote: "Normal map tangents were also not solved yet". — [blender/blender#101726](https://projects.blender.org/blender/blender/issues/101726)
- [V] State of those two routines in 5.3.0: Blender's vertex-normal code walks a vertex-to-face map and contains no atomic accumulation; Cycles' own vertex-normal fallback is a plain serial loop; but the MikkTSpace tangent generator still adds tangents with atomic float adds and switches to its parallel path when more than one thread is available and the mesh has more than 10,000 faces. — [mesh_normals.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/blenkernel/intern/mesh_normals.cc), [scene/mesh.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/scene/mesh.cpp), [mikktspace.hh](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/mikktspace/mikktspace.hh)
- [V] `-t` / `--threads <n>` sets the thread count for rendering and other operations; 0 means the machine's processor count. — [creator_args.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/creator/creator_args.cc)
- [V] `scene.cycles.scrambling_distance` (default 1.0) and `auto_scrambling_distance` (default False) trade pixel-to-pixel randomisation for GPU speed, with a warning in the description that artifacts can result; sync forces the value back to 1.0 unless the pattern is Tabulated Sobol. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [sync.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/sync.cpp)
- [V] Path guiding: `scene.cycles.use_guiding` defaults to False. `scene.cycles.use_deterministic_guiding` defaults to True and is described as making guided renders reproducible with identical pixel values, at the cost of slower training. Blender's test script notes there is no path guiding on GPU. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py)
- [V] In #101726 a contributor showed that with path guiding the tiny geometry differences compound over training iterations into visibly different noise at 32 spp. — [blender/blender#101726](https://projects.blender.org/blender/blender/issues/101726)
- [V] Other sampling switches with defaults in 5.3: `use_light_tree` True, `light_sampling_threshold` 0.01, `use_layer_samples` 'USE' (a view layer's own sample count overrides the scene's). — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] Blender 4.4 replaced the old sample offset with `use_sample_subset`, `sample_offset` and `sample_subset_length`, so that a blue-noise render can be divided across machines correctly; scripts written for the old offset need updating. — [Blender 4.4 Cycles release notes](https://developer.blender.org/docs/release_notes/4.4/cycles/), [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [S] Older tracker titles point at seed handling bugs in past versions ("seed is always animated even when disabled", T97522; "use_animated_seed is not animating", T46638). Not opened. — [T97522](https://developer.blender.org/T97522), [T46638](https://developer.blender.org/T46638)

### Inferences
- [E] Same machine, same Blender build, single device, fixed `seed`, `use_animated_seed = False`, fixed `samples`, explicit pattern, `time_limit = 0`: the path-traced pixels should be bit-identical run to run, *provided* no mesh with a tangent-space normal map exceeds 10,000 faces (or the render is launched with `-t 1`, or tangents are avoided/baked). This is the first thing the measured-test researcher should confirm, including a case with a >10,000-face normal-mapped mesh.
- [E] Thread count does not enter the sampler, so 8 versus 32 threads should give the same pixels apart from the tangent case above; Embree's BVH build is also multithreaded and is an unverified second candidate.
- [E] Adaptive sampling is not speed-dependent by design, but it amplifies cross-device float differences: a pixel that sits near the threshold can stop on one device and continue on another, so two machines can end with different per-pixel sample counts. For bit-level repeatability on one machine it is fine; for cross-machine closeness, `use_adaptive_sampling = False` with a fixed `samples` removes this amplifier.
- [E] Because the adaptive x/y filter works inside the buffer window it is given, a different `tile_size` (when the image is larger than one tile) or a different multi-device split can change which border pixels get re-opened. Pin `tile_size`, and keep the image within one tile where memory allows (default 2048 covers a 2048-px square).
- [E] Multi-device rendering (CPU+GPU, or two different GPUs) is the one configuration that is speed-dependent by construction: the split line moves with measured timings, and CPU and GPU kernels are not bit-identical (section 2). Use exactly one device per render.
- [E] Suggested pin block (5.2 LTS / 5.3 property names): `c = scene.cycles; c.seed = <fixed int>; c.use_animated_seed = False; c.sampling_pattern = 'BLUE_NOISE'` (or `'TABULATED_SOBOL'`; avoid leaving `'AUTOMATIC'` so a future change of what "automatic" means cannot move the picture); `c.samples = <fixed>; c.time_limit = 0.0; c.use_adaptive_sampling = False` (strict) or True with explicit non-zero `adaptive_threshold` and `adaptive_min_samples`; `c.scrambling_distance = 1.0; c.auto_scrambling_distance = False; c.use_guiding = False; c.use_light_tree = True; c.light_sampling_threshold = 0.01; c.use_layer_samples = 'IGNORE'; c.tile_size = 2048`; always render the same `scene.frame_current`.
- [E] Setting 0 ("automatic") for `adaptive_threshold` or `adaptive_min_samples` makes the effective value a function of other settings and of whatever formula the version uses; explicit non-zero values are safer across versions.

## 2. CPU versus GPU: bit-identical or only close? Metal versus OptiX/CUDA/HIP/oneAPI versus CPU; hardware ray tracing versus software BVH; Embree

### Takeaway
Blender does not treat CPU and GPU output as bit-identical: its own regression suite compares GPU renders to CPU references with a tolerance, and keeps per-backend lists of scenes that differ for stated precision reasons. Treat "same device type, same backend, same ray-tracing mode" as part of the render's identity; across device types expect "close", not "equal".

### Cited Findings
- [V] Blender's Cycles regression tests check every device (CPU and each GPU backend) against one stored set of reference images using OpenImageIO's diff with a tolerance, not a hash; for GPU runs the report is set up to show CPU Cycles as the comparison. The default pass rule is: fail only if more than 1% of pixels differ by more than 0.016 (on a 0–1 scale, roughly 4/255). — [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py), [render_report.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/modules/render_report.py)
- [V] The same script loosens that rule per test family: 0.032 for motion blur, integrator and displacement tests; 0.038 for shadow catcher; 0.02 with 4% of pixels for light and camera tests; 0.048 with 3% for volumes; 0.05 for colourspace; 0.05 with 4% for Gaussian splats. Comments give platform reasons, for example one caustics scene rendering "quite different" on Linux and Intel macOS versus Windows and Arm macOS, and a displacement scene differing slightly on Linux. — [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py)
- [V] Scenes excluded from GPU comparison, with the reasons written in the script: uninvestigated GPU differences in a glass-mix and a glossy-refraction scene; inconsistent hair primitives between Embree and the GPU; inconsistent handling of overlapping objects; no path guiding on GPU. OptiX: ray-intersection precision on very large triangles and planes. MetalRT: a different parameterisation of linear curves. HIP-RT: light-leak fireflies from intersection precision. All platforms: a many-lights scene excluded for high noise variance between platforms. — [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py)
- [V] The CPU device registers two builds of every kernel function, a baseline one and an AVX2 one, and picks at run time; debug switches `debug_use_cpu_avx2` and `debug_use_cpu_sse42` exist to force the choice. — [device/cpu/kernel.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/device/cpu/kernel.cpp), [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] BVH layouts in 5.3: BVH2 (Cycles' own), Embree (CPU), OptiX, Metal (MetalRT), HIPRT, and Embree-on-GPU (Intel). The Embree scene is created with Embree's "robust" flag; build quality is medium, or high when spatial splits are on. — [bvh/bvh.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/bvh/bvh.cpp), [bvh/embree.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/bvh/embree.cpp)
- [V] A kernel comment admits that Cycles' triangle test and the "custom BVH" triangle tests (the hardware ray-tracing back ends) are not numerically identical, which is why its self-intersection fallback is not ideal for them. — [kernel/integrator/shade_surface.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/integrator/shade_surface.h)
- [V] Hardware ray tracing is chosen in **user preferences**, not in the .blend: `preferences.addons['cycles'].preferences.metalrt` ('OFF' = BVH2, 'ON', 'AUTO'; default 'AUTO'), `.use_hiprt` (default True), `.use_oneapirt` (Embree on GPU, default True). `.kernel_optimization_level` (default 'FULL') lets kernels be specialised to scene content, with generic kernels used until the optimised set is ready. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] Blender 4.0: on Apple M3, MetalRT is used by default via the "Auto" setting; on M1/M2 it is supported but off by default because Cycles' own intersection code is faster there. — [Blender 4.0 Cycles release notes](https://wiki.blender.org/release_notes/4.0/cycles/)
- [V] Blender 4.4: AMD HIP RT stopped being experimental, with a note that it would become the default in the following release. — [Blender 4.4 Cycles release notes](https://developer.blender.org/docs/release_notes/4.4/cycles/)
- [S] A news headline says Blender 5.1 shipped with AMD GPU ray tracing on by default. Not opened. — [Phoronix, Blender 5.1 released](https://phoronix.com/news/blender-5.1-released)
- [V] Device selection: `scene.cycles.device` is 'CPU' or 'GPU'; 'GPU' means "whatever is enabled in preferences" (`compute_device_type` plus the per-device `use` flags). If no GPU device is enabled there, the preference device stays the CPU and the render proceeds on CPU with no error. The default compute device type is None everywhere except Apple-silicon Macs, where it is Metal. — [blender/device.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/device.cpp), [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] The command-line option `--cycles-device <CPU|CUDA|OPTIX|HIP|ONEAPI|METAL>` (given after `--`, optionally with `+CPU`) overrides both preferences and the scene setting; if no device of that type exists Cycles substitutes an error device ("Found no Cycles device of the specified type") instead of quietly using something else. — [addon/engine.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/engine.py), [blender/device.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/device.cpp)
- [V] Flamenco's FAQ tells farm operators not to pass `--factory-startup` for GPU jobs because it resets Blender to CPU rendering, and says the GPU method and device must be set in Blender's preferences on each worker. — [Flamenco FAQ](https://flamenco.blender.org/faq/)
- [V] The SheepIt farm supports only NVIDIA GPUs; its FAQ says AMD GPUs were dropped in January 2023 because HIP frames differ from CUDA/OptiX output, which made mixing them impractical. — [SheepIt FAQ](https://www.sheepit-renderfarm.com/faq)
- [V] In report T101816 (Blender 3.3.1) Cycles developer Lukas Stockner could not reproduce a CPU/GPU brightness difference and wrote that on his machine "CPU, CUDA, OPTIX and CPU+CUDA all give an identical render"; another tester did reproduce a difference on Windows. — [T101816](https://developer.blender.org/T101816)
- [V] In report #91570 (2.93.4, last tile of a CPU+GPU render lit differently) Brecht Van Lommel put the cause on a very large plane and advised subdividing large planes; the report was closed as a duplicate. — [blender/blender#91570](https://projects.blender.org/blender/blender/issues/91570)
- [V] Report #95895 (3.1 beta): "different results on different computers" turned out to be geometry, not sampling: GPU subdivision combined with autosmooth/creases produced faceted meshes on some machines; closed as a duplicate of #94921. — [blender/blender#95895](https://projects.blender.org/blender/blender/issues/95895)
- [S] Many further tracker titles report CPU/GPU mismatches over the years (T53452, #78432, T89351, T67448 "shader node float precision", T69535 "precision differences for small, far away area light", #50193 volumes). Not opened. — [T67448](https://developer.blender.org/T67448), [T69535](https://developer.blender.org/T69535), [#78432](https://projects.blender.org/blender/blender/issues/78432)
- [V] A developer-forum thread asks exactly whether two machines produce cryptographically identical pixels; the fetched page shows the question with no replies. — [devtalk: Rendered Images on Different Hardware](https://devtalk.blender.org/t/rendered-images-on-different-hardware/24300)

### Inferences
- [E] Working rule for the skill: a render's identity includes (Blender build, device type, GPU backend, hardware-RT on/off, CPU kernel variant). Bit-identity is a reasonable expectation only when all five match and the hardware/driver is the same model family; across CPU↔GPU, CUDA↔OptiX, Metal↔anything, or MetalRT on↔off, expect small numeric differences that land inside Blender's own 0.016 / 1% bar for ordinary surfaces but can be larger for the listed hard cases (big flat planes, overlapping coincident surfaces, curves, many small lights).
- [E] Two x86 machines that both have AVX2 will select the same CPU kernel; an Apple-silicon CPU runs a different (NEON) build, so Mac-CPU versus PC-CPU should be treated as different device types for tolerance purposes.
- [E] Jewelry is close to a worst case for cross-device closeness: long specular/refractive chains through gemstones turn a last-bit difference in one intersection into a different path. Expect CPU↔GPU differences to show as different *noise* in facets rather than as a brightness shift; high sample counts shrink it, denoising can then magnify what is left (section 3).
- [E] Because the hardware-RT and device choices live in user preferences, a headless job should set them in the script (`prefs = bpy.context.preferences.addons['cycles'].preferences; prefs.compute_device_type = ...; prefs.metalrt = 'OFF'`, enable devices explicitly) or use `--cycles-device`, and should log the devices actually used. Simplest catalogue rule: CPU only for masters, or one named GPU backend with hardware RT explicitly fixed.
- [E] The Metal "kernel optimisation" behaviour (generic kernels until specialised ones are compiled) means the first render after a cache clear may run partly on a different kernel build than later renders; whether pixel values differ is untested. `kernel_optimization_level = 'OFF'` would remove the question at a speed cost.

### Gaps
- No Blender manual or developer-documentation sentence stating "CPU and GPU are / are not bit-identical" was read; the manual's GPU Rendering page was unreachable. The test-suite tolerances are the strongest primary evidence found.
- No measured figure for typical CPU↔GPU pixel difference on gemstone scenes; needs the on-machine tests.
- Which BVH each GPU backend uses by default in 5.3 (for example whether CUDA and software Metal still use BVH2) was read only from enum names and preference descriptions, not traced through each device file.

## 3. Denoising: is Open Image Denoise deterministic for the same input; does it change across OIDN or Blender versions; OptiX denoiser; passes, prefilter and what to pin

### Takeaway
OIDN's documentation promises equal *quality* across devices but explicitly allows small numeric differences between CPU and GPU, and its trained models have changed between releases that different Blender versions bundle. The OptiX denoiser's model lives in the NVIDIA driver and changes with driver updates, so it cannot be pinned from Blender at all. For reproducible stills, denoise with OIDN on CPU at high quality from a pinned Blender build, and keep the noisy render plus guide passes.

### Cited Findings
- [V] OIDN's README says that in the default high quality mode results have the same quality whichever device runs it, but that hardware differences mean "there might be small numerical differences" between outputs; in balanced and fast modes larger differences across devices should be expected. — [OIDN README](https://raw.githubusercontent.com/RenderKit/oidn/master/README.md)
- [V] OIDN versions bundled with Blender, from each release's library version list: 4.2.0 → OIDN 2.3.0; 4.5.0 and 5.0.0 → 2.3.3; 5.1.0 → 2.4.1; 5.2.0 and 5.3.0 → 2.5.0. — [versions.cmake 4.2.0](https://raw.githubusercontent.com/blender/blender/v4.2.0/build_files/build_environment/cmake/versions.cmake), [4.5.0](https://raw.githubusercontent.com/blender/blender/v4.5.0/build_files/build_environment/cmake/versions.cmake), [5.0.0](https://raw.githubusercontent.com/blender/blender/v5.0.0/build_files/build_environment/cmake/versions.cmake), [5.1.0](https://raw.githubusercontent.com/blender/blender/v5.1.0/build_files/build_environment/cmake/versions.cmake), [5.2.0](https://raw.githubusercontent.com/blender/blender/v5.2.0/build_files/build_environment/cmake/versions.cmake), [5.3.0](https://raw.githubusercontent.com/blender/blender/v5.3.0/build_files/build_environment/cmake/versions.cmake)
- [V] OIDN's changelog records model changes that alter output: 2.2.0 improved denoising quality (finer detail) and added the Metal device; 2.3.0 "significantly improved" the high-quality filter for HDR colour + albedo + normal with clean auxiliary inputs, using a much heavier network, and added a fast mode. 2.5.0 lists a fix for corrupted output on Apple M5 Pro/Max GPUs. — [OIDN CHANGELOG](https://raw.githubusercontent.com/RenderKit/oidn/master/CHANGELOG.md)
- [V] Blender 4.2 LTS's notes: OIDN upgraded to 2.3 for better quality; GPU denoising extended to AMD; CPU renders may use GPU denoising; the denoiser uses the GPU device chosen in preferences (so the OptiX denoiser needs an OptiX device configured there). — [Blender 4.2 LTS Cycles release notes](https://developer.blender.org/docs/release_notes/4.2/cycles/)
- [V] Blender 4.1 introduced GPU-accelerated OIDN (NVIDIA GTX 16xx/RTX, Intel Xe-HPG and newer, Apple silicon on macOS 13+), switched on automatically for GPU viewport rendering. — [Blender 4.1 Cycles release notes](https://wiki.blender.org/release_notes/4.1/cycles/)
- [V] Final-render denoise properties and 5.3 defaults: `scene.cycles.use_denoising` True; `denoiser` OpenImageDenoise (the final-render list offers only 'OPENIMAGEDENOISE' and, with an OptiX device in preferences, 'OPTIX'); `denoising_input_passes` 'RGB_ALBEDO_NORMAL' (others: 'RGB', 'RGB_ALBEDO'); `denoising_prefilter` 'ACCURATE' (others: 'NONE', 'FAST'); `denoising_quality` 'HIGH' (others: 'BALANCED', 'FAST'); `denoising_use_gpu` False. A per-view-layer `view_layer.cycles.use_denoising` can switch it off for that layer. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [sync.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/sync.cpp)
- [V] How Cycles maps prefilter to OIDN: OIDN's clean-auxiliary flag is set whenever prefilter is not 'FAST'; 'ACCURATE' additionally runs separate albedo and normal prefilter passes first. Cycles' defaults (Accurate + albedo + normal + High) are therefore exactly the input combination whose network OIDN 2.3.0 replaced. — [denoiser_oidn.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/denoiser_oidn.cpp), [OIDN CHANGELOG](https://raw.githubusercontent.com/RenderKit/oidn/master/CHANGELOG.md)
- [V] Silent fallback: if the chosen denoiser cannot run on the selected device (OptiX denoiser without an OptiX device, GPU OIDN on an unsupported GPU), Cycles falls back to OIDN on the CPU and continues. — [denoiser.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/denoiser.cpp)
- [V] In final (background) renders the scheduler denoises only when the last sample is done. — [render_scheduler.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/integrator/render_scheduler.cpp)
- [V] OptiX denoiser: an NVIDIA engineer stated (April 2020) that the denoiser ships inside the display driver since OptiX 6.5, that different drivers can carry differently trained networks, and that an application cannot store or pin a particular network; the poster had seen denoised output change between two driver versions while the un-denoised render stayed identical. — [NVIDIA developer forum](https://forums.developer.nvidia.com/t/optix7-denoiser-different-results-with-different-version-of-drivers/117989)
- [V] Blender 4.4's notes say the OptiX denoiser was updated, and that with recent drivers even older Blender versions pick up the improved denoiser automatically; quality can drop in some scenes. Blender 5.0 flips the image vertically before OptiX denoising, which changes its result. Blender 4.5 raised the minimum OptiX driver to 535. — [4.4 notes](https://developer.blender.org/docs/release_notes/4.4/cycles/), [5.0 notes](https://developer.blender.org/docs/release_notes/5.0/cycles/), [4.5 notes](https://developer.blender.org/docs/release_notes/4.5/cycles/)
- [V] The DLSS Ray Reconstruction denoiser added in 5.3 is offered only in the viewport denoiser list, not for final renders; trade press describes it as an interactive-preview feature needing an RTX 20-series or newer card and driver 620+. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py), [CG Channel, 11 Nov 2026](https://www.cgchannel.com/?p=180007)
- [V] Per-layer switches for saving guide data exist: `view_layer.cycles.denoising_store_passes` (and related pass options). — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)

### Inferences
- [E] OIDN on CPU, same OIDN version, same thread-independent inputs: I expect run-to-run identical output (it is a fixed network evaluated without random numbers), but neither the README nor the changelog says so in words; this is a claim to measure, not to cite.
- [E] Pin list for denoising: `use_denoising = True; denoiser = 'OPENIMAGEDENOISE'; denoising_use_gpu = False; denoising_quality = 'HIGH'; denoising_prefilter = 'ACCURATE'; denoising_input_passes = 'RGB_ALBEDO_NORMAL'`. Never 'OPTIX' for catalogue masters, since a driver update on any machine changes the picture without any change to Blender or the scene.
- [E] A denoiser is a strong amplifier of tiny input differences in low-sample regions: two noisy inputs that differ in the last bits usually denoise to nearly the same image, but two inputs with *different noise* (other device, other seed) can differ visibly in gem facets. Higher `samples` before denoising is what buys cross-machine closeness.
- [E] Crossing a Blender version that changes OIDN (4.5/5.0 → 5.1 → 5.2) should be assumed to change every denoised pixel slightly even if Cycles itself rendered the same noisy image. A catalogue-wide re-render or a visual re-approval belongs in the upgrade procedure.
- [E] Archiving the noisy combined pass plus albedo and normal guide passes in a multilayer EXR beside each master allows re-denoising later with a pinned OIDN build without re-rendering, and separates "render changed" from "denoiser changed" when a regression appears.
- [E] The viewport has its own denoise settings (`preview_denoiser`, `preview_denoising_*`) with different defaults; viewport output must never be used as a deliverable.

### Gaps
- No explicit statement found from Intel that OIDN is bit-deterministic for identical input on one device, nor an OIDN issue discussing it (one search; nothing relevant surfaced).
- NVIDIA's current OptiX denoiser documentation was not read; the forum answer is from 2020, though the Blender 4.4 note is consistent with it.
- OIDN's CPU code paths differ by instruction set (the 2.5.0 changelog mentions an AMX-FP16 path on new Intel CPUs); whether two different x86 CPUs give bit-identical OIDN output is unverified.

## 4. Version pinning: do Cycles results change between Blender versions; what is current; which is the LTS; how studios and farms pin

### Takeaway
Yes: almost every release from 4.0 to 5.3 has at least one documented change to shading, sampling, denoising or colour configuration that alters pixels. On 25 November 2026 the newest release is 5.3.0 (10 November 2026); the newest LTS is 5.2 LTS (5.2.5, supported to July 2028), with 4.5 LTS (4.5.17) still receiving patches. A catalogue should pin one exact LTS patch build and treat any upgrade as a re-baseline.

**How versions get pinned**
- [V] `bpy` on PyPI ("Blender as a Python module") carries exact Blender versions, so `bpy==5.2.5` pins a build. 5.1 and later wheels are CPython 3.13 only (4.x and 5.0 are 3.11 only). 5.3.0 wheels exist for macOS arm64 (13.0+), Linux x86_64 (manylinux_2_28), Windows amd64 and Windows arm64; neither 5.3.0 nor 5.2.5 has an Intel-Mac or Linux-arm64 wheel (4.5.17 still has an Intel-Mac one). — [PyPI bpy JSON](https://pypi.org/pypi/bpy/json)
- [V] A script can check what it is running on: `bpy.app.version`, `version_string`, `version_cycle`, `build_hash`, `build_commit_date`, `build_branch`, `build_platform`, plus `bpy.app.background` and `bpy.app.factory_startup`. — [bpy_app.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/python/intern/bpy_app.cc)
- [V] Flamenco (Blender Studio's farm manager): the `blender` variable in `flamenco-manager.yaml` can be the bare word `blender` (worker then uses the .blend file association on Windows, else whatever is on PATH) or an explicit per-platform path, used verbatim; the docs' example points every platform at one specific release. Default arguments are `-b -y`. — [Flamenco: Blender variable](https://flamenco.blender.org/usage/variables/blender)
- [V] Flamenco does not split one frame across machines out of the box. — [Flamenco FAQ](https://flamenco.blender.org/faq/)
- [V] SheepIt: uses unmodified official Blender Foundation releases that the client downloads itself; the Blender version is detected from the project and can be overridden by the owner; betas and daily builds are not offered; owners cannot run their own scripts. It splits frames either into a tile grid or into layers rendered with different seeds and merged. — [SheepIt FAQ](https://www.sheepit-renderfarm.com/faq)
- [V] A commercial farm's guidance (iRender, 28 Aug 2026) lists version and plug-in drift, missing asset paths, a different OpenColorIO config, and unlocked sample/denoiser/device settings as the usual reasons a farm render differs from the local one; it advises recording exact versions, packing or relativising assets, locking sampling/denoiser/device, and rendering one test frame for comparison first. — [iRender blog](https://irendering.net/the-render-came-back-looking-different-why-farms-dont-match-your-scene/)

### Inferences
- [E] Recommended pin for a catalogue started now: Blender **5.2 LTS at one exact patch (5.2.5)**, held until a deliberate re-baseline. 5.3 is the only version with native dispersion (relevant for diamond "fire"), but it is two weeks old and not an LTS; if dispersion is wanted, pin 5.3.x knowingly and accept that it leaves the LTS track until the next LTS.
- [E] LTS patch releases are bug-fix releases, but a bug fix in a shader or sampler still changes pixels. Pin the patch number, not just "5.2 LTS", and re-run the reference comparison before moving 5.2.5 → 5.2.6.
- [E] Practical mechanisms: (a) keep the portable archive (zip/tar.xz/dmg) of the exact build beside the pipeline and record its file hash and `bpy.app.build_hash`; never rely on an auto-updating install (Steam, Snap, Microsoft Store); (b) or a virtual environment with `bpy==X.Y.Z` on Python 3.13; (c) first lines of every render script: compare `bpy.app.version` and `bpy.app.build_hash` to the lock file and exit non-zero on mismatch.
- [E] Opening and re-saving the master .blend in a newer Blender runs versioning code that rewrites settings; keep masters saved by the pinned version and open them read-only in the pipeline.
- [E] The portable archives are published under download.blender.org/release/ by version; this is working knowledge, not checked here.

### Gaps
- The official Blender 5.3 release notes for rendering (`https://developer.blender.org/docs/release_notes/5.3/rendering/`) and the 5.3 index (`https://developer.blender.org/docs/release_notes/5.3/`) could not be opened: the fetch tool refused both URLs pending a user permission that was not answered. 5.3 Cycles facts above come from source and trade press instead.
- Cycles release notes for 4.3, 5.1 and the Cycles-specific page for 5.2 were not found by search and were not read, so output-changing items in those three releases are missing from the list.
- Blender's written LTS policy (length, scope of fixes) was not read; only the 5.2 page's support date was.
- Whether two different *patch* builds of one LTS produce bit-identical Cycles output in practice is untested.

## 5. Scene-side sources of non-determinism

### Takeaway
Most scene-side drift is not randomness but hidden inputs: object names feed the per-object random value, user preferences and environment variables feed device and colour choices, missing files fall back quietly, and old files are rewritten on load. One genuinely non-deterministic piece remains in 5.3 (parallel tangent accumulation on large meshes).

### Cited Findings
- [V] `Object Info > Random` for an ordinary (non-instanced) object is a hash of the object's **name**; for instances it is the instancer-provided random id. Renaming an object, or importing it as "Ring.001" instead of "Ring", changes every material that uses that output. — [blender/object.cpp](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/object.cpp)
- [V] Tangent-space generation (MikkTSpace; my note: this is the data tangent-space normal maps rely on) still accumulates with atomic float adds on a parallel path when the mesh has more than 10,000 faces and more than one thread is available. — [mikktspace.hh](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/mikktspace/mikktspace.hh)
- [V] Blender starts its embedded Python in an isolated configuration by default, ignoring `PYTHON*` environment variables unless `--python-use-system-env` is passed; the interpreter set-up code sets no fixed hash seed. — [bpy_interface.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/python/intern/bpy_interface.cc), [creator_args.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/creator/creator_args.cc)
- [V] `scene.render.use_persistent_data` keeps render data in memory between renders for faster re-renders, at a memory cost. — [rna_scene.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/makesrna/intern/rna_scene.cc)
- [V] GPU subdivision (a viewport/user-preference feature) once changed final Cycles geometry on some machines when combined with autosmooth and creases (3.1 beta, #95895). — [blender/blender#95895](https://projects.blender.org/blender/blender/issues/95895)
- [V] Missing external files do not stop a render: a farm guide notes the renderer falls back to a default, and that missing materials show as hot pink in Blender; Blender's File > External Data menu has Make All Paths Relative, Pack Resources and Find Missing Files. — [iRender blog](https://irendering.net/the-render-came-back-looking-different-why-farms-dont-match-your-scene/)
- [V] Flamenco assumes absolute asset paths are valid on every worker and does not copy such assets to shared storage. — [Flamenco FAQ](https://flamenco.blender.org/faq/)
- [V] Camera data defaults in 5.3: `clip_start` 0.1, `clip_end` 1000.0 (scene units), `lens` 50 mm. — [DNA_camera_types.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/makesdna/DNA_camera_types.h)
- [V] Self-intersection handling in 5.3: Cycles normally applies **no** ray offset on triangles (the hit primitive is excluded by id). Only when a re-test shows float error would make the ray hit a neighbouring triangle does it nudge the origin, using the "Fast and Robust Method" from Ray Tracing Gems: for a coordinate whose magnitude is below 1/32 scene unit the nudge is a fixed 1/65536 unit along the normal; above that it is a relative step of 256 float increments. — [kernel/integrator/shade_surface.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/integrator/shade_surface.h), [kernel/bvh/util.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/kernel/bvh/util.h)

- [V] Overlapping (coincident) objects are handled inconsistently between platforms and between CPU and GPU, per the comments in Blender's test blocklists. — [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py)
- [V] Blender 5.2 added a Time node to shader nodes, a new way for a material to depend on the frame. — [Blender 5.2 LTS Rendering release notes](https://developer.blender.org/docs/release_notes/5.2/rendering/)

### Inferences
- [E] Python: with no fixed hash seed, `hash("name")` and the iteration order of a `set` of strings differ between Blender launches, and `PYTHONHASHSEED` in the shell is ignored unless `--python-use-system-env` is given. Scripts must not derive seeds from `hash()`, must iterate `sorted(...)` collections, and must seed their own generators (`random.Random(1234)`, `numpy.random.default_rng(1234)`); for per-object seeds use a stable digest such as `zlib.crc32(name.encode())`. (Quick check for the test researcher: run `blender -b --python-expr "print(hash('a'))"` twice.)
- [E] Naming is an input. Import and scene-build scripts must give objects fixed names (no reliance on Blender's `.001` suffixing, which depends on what already exists in the file) and should avoid `Object Info > Random` in catalogue materials, or drive variation from an explicit custom property instead.
- [E] Procedural texture nodes (Noise, Voronoi, White Noise, etc.) are pure functions of their inputs with no hidden seed; they repeat exactly on one device, but their float evaluation can differ in the last bits between CPU and GPU. The hidden inputs are the coordinates: Generated coordinates depend on the bounding box, Object coordinates on unapplied transforms.
- [E] Seeds that must be fixed if the features are used: particle systems (`particle_system.seed`), Geometry Nodes random nodes (Seed input plus element ID; changing topology or point order changes results), any modifier with a seed (for example Displace with a random texture, Build, Decimate collapse order is deterministic but version-dependent), physics caches (bake them).
- [E] Frame-dependent values: drivers using `frame`, `#frame` expressions in node fields, keyframes, the shader Time node, `use_animated_seed`, physics. For stills, render one fixed frame number (for example frame 1) always, and do not rely on "current frame as saved".
- [E] `use_persistent_data`: for a batch that renders many pieces in one Blender session it can let state from the previous render (cached BVH, images) carry over; a fresh process per piece with `use_persistent_data = False` is the conservative choice. No report of pixel differences was found; this is caution, not evidence.
- [E] Paths: store textures and HDRIs with `//` relative paths or pack them into the .blend; before rendering, have the script walk `bpy.data.images` (and libraries, caches) and abort if any `filepath` does not exist or `image.has_data` is false after load; record a hash of each input file in the manifest. A missing HDRI otherwise yields a flat magenta-lit product that still "renders successfully".
- [E] Normals and transforms: apply scale (and ideally rotation) on meshes so bevels, displacement, bump strength and Object-space textures do not depend on object scale; set shading (smooth-by-angle or custom normals) explicitly in the build script rather than relying on importer defaults, which have changed across versions (the 4.1 removal of mesh auto-smooth is working knowledge, not checked here); keep modifier stacks in a fixed order and prefer applying them in the master file.
- [E] Millimetre-scale jewelry and float precision: single-precision floats carry about 7 significant digits wherever the object sits, so a 20 mm ring modelled at true scale in metres (coordinates around 0.01) has a resolution on the order of a nanometre; raw precision is not the problem. What matters: (1) keep the piece at the world origin, since precision is lost with distance from origin, not with small size; (2) the camera `clip_start` default of 0.1 units will clip a macro shot at true scale, so set it explicitly (for example 0.001 m) and `clip_end` to a few metres; clipping range does not affect Cycles' intersection precision the way it affects a z-buffer, it only cuts rays; (3) the rare-case self-intersection nudge is a fixed 1/65536 unit for coordinates under 1/32 unit: at true metre scale that is about 15 micrometres, which is not negligible beside pavé seats or millgrain; modelling in millimetres-as-units (ring about 20 units across, scene `unit_settings.scale_length = 0.001`) puts coordinates above 1/32 and makes the nudge relative (roughly 1.5e-5 to 3e-5 of the coordinate, i.e. a fraction of a micrometre for a coordinate of 10 mm). This is an inference from the code and should be confirmed by test before the skill mandates a unit convention; (4) avoid huge backdrop planes made of two triangles (subdivide or keep them a sane multiple of the piece size); (5) avoid exactly coincident surfaces (stone sitting flush in its seat, liquid/glass interfaces): leave a real gap or a deliberate overlap, since coincident geometry is where devices disagree.
- [E] Volume absorption inside gems and subsurface radii are in scene units, so whichever unit convention is chosen must be fixed for the whole catalogue and written into the lock file.
- [E] User preferences and add-ons are hidden inputs (compute device, hardware RT, GPU subdivision, enabled add-ons that register handlers). `--factory-startup` removes them; then set what is needed explicitly in the script.

- Auto-smooth/normals history and importer-default changes were not verified against release notes.
- The Blender manual pages on relative paths and missing files could not be read (host unreachable); the missing-file behaviour is cited from a farm's blog, not from Blender documentation.
- Geometry Nodes and particle determinism claims are working knowledge with no source opened.

## 6. Colour and output: OCIO config, view transform, look, display; file format, bit depth, compression, profiles; dithering; metadata that changes bytes

### Takeaway
The pixel pipeline after Cycles (view transform, dithering, encoding) is deterministic in 5.3, including dithering, which is a hash of pixel position with no seed. What breaks byte-equality is metadata that is on by default (date, render time, peak memory, file path) and what breaks colour consistency is an unpinned OpenColorIO configuration, which an environment variable or a 5.3 project can replace.

### Cited Findings

### Inferences
- [E] To make file hashes comparable for PNG/JPEG: set every `use_stamp_*` listed above to False and leave `use_stamp_labels = True` and `use_stamp = False`, so no stamp bit remains and no text metadata is written. Then the file bytes depend only on pixels, encoder version, compression level and the embedded profile.
- [E] Multilayer EXR is likely to keep carrying Cycles' render-time strings even with all stamps off, because that writer receives the stamp data without the gate; expect EXR *file* hashes to differ between runs and compare EXR *pixels* instead (or strip metadata in a post-step). To be confirmed by test.
- [E] Prefer comparing a hash of decoded pixel data (for example SHA-256 over the raw array from OpenImageIO or numpy) rather than the file hash; it survives harmless differences in zlib/libpng versions, compression level and metadata. Use the file hash only as a same-build regression check.
- [E] Pin colour explicitly in the script every time, never from file defaults: `display_settings.display_device = 'sRGB'`; `view_settings.view_transform = <one of 'Standard', 'AgX', 'Khronos PBR Neutral', 'Filmic'>`; `view_settings.look = 'None'`; `exposure = 0.0`; `gamma = 1.0`; `use_curve_mapping = False`; `use_white_balance = False`; `image_settings.color_management = 'FOLLOW_SCENE'`. For product shots on white where the piece's own colours should stay faithful, 'Standard' (plain sRGB, clips highlights) or 'Khronos PBR Neutral' (designed for colour-faithful product display; in the bundled config only for the sRGB display, from 4.2) are the usual candidates; AgX and Filmic desaturate bright colours by design. The choice is taste; the point here is that it be one value for the whole catalogue.
- [E] Guard the OCIO config: in the launcher, unset `OCIO` and `BLENDER_OCIO` (or set `BLENDER_OCIO` deliberately to a vendored copy), do not place catalogue files inside a 5.3 project with a custom config unless that is the intent, and write the SHA-256 of the config file actually in use into the manifest. Vendoring one `config.ocio` (plus its LUT folder) with the pipeline is the only way to keep the view transform fixed across a Blender upgrade, and even then the OpenColorIO library version can alter results in the last bits.
- [E] Dithering is safe for determinism. It does, however, turn sub-level float differences between machines into ±1 code-value flips in 8-bit output; for the cross-machine metric either accept ±1/255 or render comparison images with `dither_intensity = 0.0` (at the risk of visible banding on smooth white backdrops in the deliverable; keep dithering on for delivery).
- [E] Formats: master = 16-bit float OpenEXR (lossless codec such as ZIP), scene-linear, with denoising guide passes; deliverable PNG 8-bit (or 16-bit) RGB/RGBA derived from the master with the pinned view transform; JPEG/WebP only as a last, lossy derivative produced by one pinned encoder. JPEG encoding is deterministic for one encoder build but not across library versions. EXR lossy codecs (DWAA/DWAB, and any newer lossy option) should be avoided for masters.
- [E] Embedded ICC/CICP data changes file bytes relative to a version that did not embed it, even for identical pixels (from which version each profile is embedded was not established) and changes how colour-managed browsers interpret the PNG; decide once whether web deliverables carry the sRGB profile and keep it constant.
- [E] Transparent-background product shots add alpha handling as another thing to pin (`film_transparent`, PNG RGBA, straight versus premultiplied on conversion).

- I did not read release notes stating in which version ICC/CICP embedding began; the claim is limited to "present in 5.3 source, no ICC entries in the 5.0.0 config".

## 7. Verification practice: how to test reproducibility, metrics and tolerances, manifests, headless command lines

### Takeaway
Blender's own practice is the model: launch headless with factory settings, render to PNG, and compare against a stored reference with an absolute-difference threshold plus an allowed fraction of pixels (0.016 and 1% by default), not with a hash. For a product catalogue use two tiers: exact pixel equality on the same build and device, and a tight numeric tolerance across machines.

### Cited Findings
- [V] Blender's render tests launch each scene as: `--background --factory-startup --enable-autoexec --debug-memory --debug-exit-on-error --console-crash-handler <file> -E CYCLES -o <output> -F PNG`, then extra `--python-expr` lines that set hardware-RT preferences explicitly, then `-f 1`, and the device after `--` as `--cycles-device <DEVICE>`. — [cycles_render_tests.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/cycles_render_tests.py)
- [V] The comparison is `oiiotool <ref> <new> --fail <threshold> --failpercent <percent> --diff`, with defaults 0.016 and 1; the report extracts the maximum error and the count of pixels over threshold. — [render_report.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/tests/python/modules/render_report.py)
- [V] OpenImageIO's `idiff` reports mean error, RMS error, peak SNR, maximum error with its pixel and channel, and counts over the warn/fail thresholds. By default any pixel differing by more than a tiny epsilon fails. Options: `-fail A`, `-failrelative R`, `-failpercent P`, `-hardfail H` (any single pixel beyond H fails), matching `-warn*` options, `--allowfailures N`, `-p` for a perceptual test (Yee's metric), `-o`/`-abs`/`-scale` for a difference image. It compares pixel values only, not metadata. Its docs give 0.004 as "just above" one 8-bit step. — [idiff documentation, OIIO 3.1](https://raw.githubusercontent.com/AcademySoftwareFoundation/OpenImageIO/v3.1.7.0/src/doc/idiff.rst)
- [V] NVIDIA's FLIP is a perceptual difference evaluator with LDR and HDR variants; `pip install flip-evaluator` provides a `flip -r reference.png -t test.png` tool (Python 3.10+); version 1.7 was published on PyPI on 7 November 2025. — [FLIP README](https://raw.githubusercontent.com/NVlabs/flip/main/README.md), [PyPI flip-evaluator JSON](https://pypi.org/pypi/flip-evaluator/json)
- [V] Command-line facts for 5.3: `-b`/`--background` runs without UI (audio off by default in this mode); `-noaudio` forces the sound system to None; `--factory-startup` skips the user's startup file (and the code path also stops preferences being saved on exit); `-P`/`--python <file>` runs a script; `--python-expr` runs an expression; `--python-exit-code <0..255>` makes Blender exit with that code if a command-line script raises; `-t`/`--threads`; `-E` engine; `-o` output path (`//` is relative to the .blend, `#` is frame padding); `-F` format; `-x` extension toggle; `-f` frame; `--addons` enables extra add-ons; `-y`/`-Y` enable/disable automatic script execution. — [creator_args.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/creator/creator_args.cc)
- [V] Arguments after `--` are left for scripts; Cycles itself reads `--cycles-device` and `--cycles-print-stats` from there. — [addon/engine.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/engine.py)
- [V] Flamenco's default Blender arguments are `-b -y`; its FAQ warns that `--factory-startup` drops GPU configuration. — [Flamenco: Blender variable](https://flamenco.blender.org/usage/variables/blender), [Flamenco FAQ](https://flamenco.blender.org/faq/)
- [V] In #101726 the diagnostic method that located the non-determinism was: render twice at low sample count, diff and scale the difference image, then repeat with `-t 1` and with features (path guiding) switched off. — [blender/blender#101726](https://projects.blender.org/blender/blender/issues/101726)
- [V] A commercial farm recommends rendering a single test frame at the destination and comparing it with the local render before committing a job. — [iRender blog](https://irendering.net/the-render-came-back-looking-different-why-farms-dont-match-your-scene/)

### Inferences
- [E] Canonical launch line for the skill: `blender -b --factory-startup -noaudio --python-exit-code 1 master.blend -P render_piece.py -- --piece <id> --out <dir> --cycles-device CPU`. Order matters: options are processed left to right, so the .blend comes before `-P`, and `--python-exit-code` before the script. With `--factory-startup` the script itself must enable any GPU device and any add-on it needs; `-y` should be avoided unless the master file genuinely needs embedded scripts or drivers, in which case the file must be trusted and its scripts hashed too.
- [E] The script, not the file, should be the single place that sets every pinned value from a lock file (sections 1, 3, 6), then asserts by reading the values back, then renders with `bpy.ops.render.render(write_still=True)`.
- [E] Test ladder, cheapest first: (1) same machine, same build, render twice: decoded-pixel SHA-256 must match; if not, repeat with `-t 1`, then with denoising off, then with normal maps removed, to find the cause; (2) same build on a second machine of the same device type: compare with a metric; (3) other device type: metric, wider tolerance; (4) after any Blender or driver change: full reference-set comparison.
- [E] Suggested tolerances, to be calibrated against the measured tests on this machine: Tier A (same build, same device, same machine): zero difference, compare hashes. Tier B (same build and device type, other machine), on 8-bit output: fail if any pixel differs by more than 4/255 or more than 0.5% of pixels differ by more than 1/255 (`idiff -fail 0.004 -failpercent 0.5 -hardfail 0.016`); mean absolute error below about 0.001. Tier C (other device type or re-baseline after an upgrade): start from Blender's own 0.016 / 1% and add a perceptual check (mean FLIP below roughly 0.02–0.03, SSIM above roughly 0.995) plus a human look at gemstone facets and metal edges, which a global metric averages away. These numbers are my estimates, not sourced thresholds.
- [E] Compare on the final 8-bit image for "does the customer see the same picture", and on the linear EXR (relative error) for "did the renderer change"; the two can disagree because the view transform compresses highlights.
- [E] Per-render manifest (JSON beside each image): Blender `version_string`, `build_hash`, `build_commit_date`, `build_platform`; OS and CPU model; device type and device names actually used, hardware-RT setting, GPU driver version; thread count; OIDN/denoiser settings; seed, samples, pattern, adaptive settings, time limit, tile size; resolution and percentage, frame number; view transform, look, exposure, display, OCIO config path and SHA-256, relevant environment variables; SHA-256 of the master .blend, of the rig/library .blend files, of every texture and HDRI, of the source CAD/mesh file and of the render script and lock file; SHA-256 of the output's decoded pixels and of the file; wall-clock render time (kept here, not in the image).
- [E] Keep a small fixed "golden set" (for example one plain band, one pavé piece, one large solitaire, one coloured-stone piece) whose reference renders are stored with the pipeline; run it on every machine and after every change, the way Blender runs its own render tests.

## 8. Catalogue consistency: reusable camera and light rigs, fixed focal length and distance rules, a locked look file

### Takeaway
No primary source was consulted that prescribes a catalogue rig; what the evidence in sections 1–7 supports is the mechanism: one hashed rig-and-look library plus one lock file of settings, applied by script to every piece, with the script refusing to render on any drift. The specifics below are engineering proposals.

### Cited Findings
- [V] Scene-level look controls that a lock file would carry exist as discrete properties: view transform, look, exposure, gamma, curves and white balance on `scene.view_settings`; display on `scene.display_settings`; Cycles film exposure on `scene.cycles.film_exposure`. — [rna_color.cc](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/makesrna/intern/rna_color.cc), [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] Camera data carries `lens`, `sensor_x` (sensor width), `clip_start` and `clip_end` with defaults 50 mm, the default sensor width, 0.1 and 1000. — [DNA_camera_types.h](https://raw.githubusercontent.com/blender/blender/v5.3.0/source/blender/makesdna/DNA_camera_types.h)
- [V] Per-view-layer sample overrides exist and are honoured by default (`use_layer_samples = 'USE'`), so a rig file's view layers can silently change sampling. — [properties.py](https://raw.githubusercontent.com/blender/blender/v5.3.0/intern/cycles/blender/addon/properties.py)
- [V] Blender 5.3's opt-in Project system can hold project-wide settings including the OpenColorIO configuration and custom path variables such as `{project_root}`. — [Blender 5.3 Core release notes](https://developer.blender.org/docs/release_notes/5.3/core/)
- [V] Farm practice treats locked sample count, denoiser and device, matched versions and matched colour configuration as the preconditions for consistent output. — [iRender blog](https://irendering.net/the-render-came-back-looking-different-why-farms-dont-match-your-scene/)

### Inferences
- [E] Structure: (1) `studio_rig.blend` holding named camera rigs, lights, world/HDRI, backdrop and shadow catcher, one collection per shot type (hero three-quarter, top-down, side profile, detail macro, on-white packshot); (2) `look.lock.json` holding every pinned value from sections 1, 3 and 6 plus the Blender build hash; (3) a material library .blend for metals and stones. Each piece's scene links (not appends) the rig and materials, so there is exactly one copy to hash. The render script applies the lock, reads values back, and aborts on mismatch.
- [E] Camera rule: fixed focal length and sensor for each shot type (a long lens, in the region of 85–105 mm on a 36 mm sensor, keeps perspective distortion low on small objects; the exact figure is a taste decision to make once), fixed f-stop or depth of field off, fixed aspect and resolution with `resolution_percentage = 100`. Distance is computed, not eyeballed: with the piece's bounding-sphere radius r and a fixed fill fraction k of the vertical field of view θ, camera distance d = r / sin(k·θ/2), aimed at the bounding-sphere centre. Every piece then occupies the same fraction of the frame.
- [E] Scale the rig with the piece: place lights at fixed directions relative to the camera and at distances proportional to r, with area-light size proportional to r and power proportional to r² (Blender area-light power is total watts, so this keeps brightness on the piece and highlight shape constant from a 6 mm stud to a 60 mm bangle). Alternatively keep one physical rig size and accept that small pieces see larger, softer sources; either is fine if it is one rule.
- [E] Orientation and placement conventions per category (ring: band axis and head direction; pendant: bail up; earrings: pair spacing as a multiple of r), origin at the bounding-box centre resting on the ground plane, set by script from the mesh, never by hand.
- [E] HDRI: one file, hashed, fixed rotation and strength, colour space set explicitly on the image datablock; avoid per-piece HDRI tweaks. Gem appearance is dominated by what the environment contains, so this file is as much a part of the "look" as the view transform.
- [E] Materials: metals and stones come only from the linked library; per-piece variation is a parameter choice from a fixed list (alloy, stone type), not ad-hoc node edits. Fix IOR, dispersion (if on 5.3), absorption colour/density per stone type in the library.
- [E] Catalogue consistency is a stronger requirement than run-to-run determinism in one respect: a Blender or OIDN upgrade that is deterministic within itself still makes new pieces look different from old ones. Either freeze the build for the life of the catalogue, or re-render the whole catalogue from the stored scenes at each re-baseline; keeping every piece's scene, inputs and manifest is what makes the second option possible.
- [E] If the 5.3 Project system is adopted, the project's OCIO setting becomes one more hashed input; on 5.2 LTS it does not exist and the launcher's environment plus the bundled config decide colour.
