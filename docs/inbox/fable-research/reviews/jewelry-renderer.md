# Review of docs/plans/jewelry-renderer.md

Verdict: **ready after fixes.** Step 1 and founder check F0 can start today. Nothing from step 2 on should start until the build loop has a real GPU in it, F0 is hardened and run first, and the gates and the plan B switch rule are repaired. No licence blocker was found; the GPL boundary holds as written.

## Suspicions, not verified

1. **"Sparkle lights reach only stones, so they cannot speckle the ground" (§4.3 Caustics).** A path ground → stone → sparkle light ends at the light from a stone. If Cycles' light linking tests the last surface, the reference will carry these speckles, and so will our kernel unless it tests the whole path. The Blender manual page I opened does not say how linking treats indirect paths. Check with a fixture before caps are frozen.
2. **Rough metal energy.** Blender's metal shader may default to a multiple-scattering GGX. The plan's conductor model names none, so satin and matte finishes could render darker than the reference. No matte fixture exists to catch it.
3. **Three WGSL compilers.** I expect differences between wgpu's, Chrome's and Safari's shader front ends on a large kernel (loops, local arrays as in the spike's `gold()`). Not tested.
4. **Background tabs and workers.** "A hidden tab keeps going in the worker" is `[E]` in the plan. Browser throttling of timers and of GPU work for hidden or occluded windows may slow or stop a long take.
5. **WebGPU inside workers in Safari 26 and Firefox.** The specification exposes it; I did not confirm either browser ships it. The plan has a main-thread fallback.
6. **F0 dispatch size.** Runs A and C submit a full 1024 × 1024 frame at 4 samples per pass. On a slow GPU a single pass may run for seconds and hit the system's GPU time-out, which would read as "does not run on Metal" (red) when slicing would have fixed it.
7. **The colour-matching fit.** The constants in `ptgem.wgsl` are from a journal paper. I could not open the journal's licence page. Constants are facts, so the risk is low; the plan already sends it to counsel.
8. **Stones that touch or overlap** each other or sit inside metal. The tracer's "inside a stone" state needs a rule for nested or overlapping stones. The plan tests a bezel only.
9. **ONNX runtime threads.** Its threaded WASM needs cross-origin isolation, which research 18 rejects. Single-thread with the WebGPU back end should work; the 5 s denoise mark depends on it.
10. **Triangle counts.** I could not measure a real 2,000 or 5,000-stone piece at production tessellation. If it passes 2 M triangles the scene budget and the 128 MB binding limit both fail. Step 4 will find out; better to know before.
11. **Metal in the `bpy` wheel.** I assume the macOS wheel renders on Metal when run headless. If not, run B has no GPU figure (see finding 2).
12. **Neutral within 1/255 of Blender.** Blender applies it through its colour configuration; a closed formula may differ by more than one code value at the shoulder.

## Lenses with nothing found

- **Terms of service.** Stages 1–4 add no third-party service or API. Render-node providers belong to the deploy plan and research 18. (The H.264 point in finding 15 is patent licensing, not a service's terms.)
- **Safety.** The renderer draws CAD; it adds no people, likeness or physical output. The one consistency point (a time cap against multi-hour animation) is in finding 10.
- **Licences, blockers.** None found. Every component of plan A that I opened is MIT, BSD, Apache-2.0, MPL-2.0 or CC0. The GPL boundary as written is sound: the worker stays a separate program, the spike's `render_cycles.py` is research only and request 3 covers it. The risk is in execution (finding 8a), not in the design.
- **Credentials and tokens.** No secret, token or key is added in stages 1–4. Stage 5 inherits the deploy plan's node tokens unchanged.
